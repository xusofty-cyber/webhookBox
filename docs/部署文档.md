# HookBox 部署文档

> 版本 0.1.0 ｜ 编写日期 2026-10-21 ｜ 适用环境 Ubuntu 22.04+ / Docker 24+

---

## 一、这个系统在解决什么问题

手机在运营商 NAT 后面，没有公网 IP，外部请求进不来；即使打洞成功，Wi-Fi 和 4G 切换会换 IP，Android 的 Doze 机制会回收后台进程。所以**手机不能自己当 webhook 服务端**。

正确做法是：公网入口 + 中转 + 一条能把手机叫醒的推送通道。

```
┌──────────────┐   POST /hook/<source>   ┌─────────────────────┐
│ 平台          │ ──────────────────────► │ 中转层               │
│ GitHub        │   (HTTPS)               │ 验签 → 归一化 → 落库  │
│ Stripe        │                         │ 幂等去重             │
│ 监控告警       │ ◄────────────────────── │ 立刻返回 200         │
└──────────────┘        200 OK            └──────────┬──────────┘
                                                     │ 实时广播
                                                     ▼
                                          ┌─────────────────────┐
                                          │ 长连接中枢           │
                                          │ WebSocket Hub       │
                                          └──────────┬──────────┘
                                                     │ WSS
                                                     ▼
                                          ┌─────────────────────┐
                                          │ 安卓 App            │
                                          │ 前台服务常驻         │
                                          │ Room 本地库         │
                                          │ 系统通知            │
                                          └─────────────────────┘
```

中转层有两套实现，**协议完全一致**，安卓端不用改，选一套部署即可。

| | Worker 版 | 自托管版 |
|---|---|---|
| 技术栈 | TypeScript + Cloudflare Workers | Go + SQLite |
| 存储 | D1（SQLite） | SQLite 单文件 |
| 长连接 | Durable Object | 进程内 Hub |
| 冷启动 | 无 | 无（常驻进程） |
| 内存占用 | — | 约 2.5 MB |
| 多实例横向扩展 | 天然支持 | 不支持（Hub 在内存里） |
| 成本 | 免费额度内基本零成本 | 服务器本身成本 |
| 运维负担 | 零 | 自己管（日志、备份、升级） |
| 数据主权 | 数据在 Cloudflare | 数据在自己磁盘 |
| 适用 | 不想运维、要弹性 | 已有服务器、要自己攥着数据 |

本次实际部署用的是**自托管版**。

## 二、接口与协议

### 2.1 HTTP 接口

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| POST | `/hook/{source}` | 接收 webhook，`{source}` 只是标签，随意起 | 见 2.3 |
| GET | `/ws?token=` | 安卓端长连接 | token |
| GET | `/api/messages?token=&before=&limit=` | 断线补拉历史 | token |
| GET | `/healthz` | 健康检查，返回 `ok` | 无 |

`limit` 默认 50，上限 200。`before` 是毫秒时间戳，取该时刻之前的消息。

### 2.2 消息格式

统一后的消息结构：

```json
{
  "id": "test:59f868fac2a4ec71cf8bc0e26d2b1e84",
  "source": "github",
  "title": "GitHub · acme/api",
  "body": "build completed / failure",
  "level": "error",
  "ts": 1792569551618
}
```

- `level` 只有三种：`info` / `warn` / `error`，决定 App 里左侧色条和通知优先级
- `title` 最长 120 字符，`body` 最长 2000 字符，超出截断
- 请求体上限 1MB，超出返回 413

### 2.3 验签规则

按优先级依次尝试，命中即通过：

| 顺序 | 条件 | 校验方式 |
|---|---|---|
| 1 | `source == "github"` 且配置了 `GITHUB_SECRET` | HMAC-SHA256，比对 `X-Hub-Signature-256` |
| 2 | `source == "gitlab"` 且配置了 `GENERIC_SECRET` | 明文比对 `X-Gitlab-Token` |
| 3 | 配置了 `GENERIC_SECRET` 且请求带 `X-HookBox-Signature` | HMAC-SHA256 十六进制 |
| 4 | 以上都不满足 | 比对 URL 上的 `?token=<RELAY_TOKEN>` |

第 4 条是兜底，因为很多平台只允许填一个回调地址，没有自定义 header 的能力。**能用签名就用签名**，URL token 会留在平台后台和访问日志里。

### 2.4 去重规则

`id` 是主键，`INSERT OR IGNORE`，重复的返回 `duplicate: true` 且不重复入库、不重复推送。

| 场景 | id 生成方式 |
|---|---|
| GitHub | 优先用 `X-GitHub-Delivery` 头，没有则 `github:<body 的 sha256>` |
| 其他平台 | 有 `payload.id` 用 `{source}:{id}`，否则 `{source}:<body 的 sha256>` |

平台超时重投是常态（GitHub 10 秒超时），这条规则保证同一条通知只到手机一次。

### 2.5 WebSocket 协议

服务端 → 客户端：

```json
{"type":"hello","ts":1792569550421}
{"type":"msg","data":{ ...消息结构... }}
```

客户端不需要发任何应用层心跳。服务端每 30 秒发一次 WebSocket Ping，客户端回 Pong；90 秒收不到 Pong 就断开。

## 三、部署前准备

### 3.1 服务器要求

| 项 | 最低 | 建议 |
|---|---|---|
| CPU | 1 核 | 1 核足够 |
| 内存 | 128 MB（仅运行） | — |
| 磁盘 | 100 MB | — |
| 系统 | 任意 Linux | Ubuntu 22.04+ |
| Docker | 20.10+ | 24+ |
| Docker Compose | v2（`docker compose` 子命令） | — |

> **如果打算在服务器上从源码构建**，编译 `modernc.org/sqlite` 需要 1.5GB 以上空闲内存，2GB 的机器大概率 OOM。推荐在本地交叉编译后上传二进制（见 5.1）。

### 3.2 域名与证书

安卓端走 `wss://`，**必须有可信证书**。三条路：

| 方案 | 需要什么 | 说明 |
|---|---|---|
| 已有域名 + 已有证书 | 域名解析到服务器 | 最省事，本次采用 |
| 已有域名 + Let's Encrypt | 80 端口可用 | `certbot --nginx` 一条命令 |
| Cloudflare Tunnel | 无 | 不用开端口，但流量过 Cloudflare |

自签证书不行，Android 会直接拒绝连接。

### 3.3 端口规划

| 端口 | 用途 | 是否对外 |
|---|---|---|
| 443 | nginx 终结 TLS | 是 |
| 80 | HTTP → HTTPS 跳转 / ACME 验证 | 是 |
| 18080 | HookBox 容器，只绑 127.0.0.1 | 否 |
| 22 | SSH | 是 |

容器**不直接对外**，一律经过宿主机 nginx。这样 TLS、限流、访问日志都集中在一处。

## 四、方案 A：部署到 Cloudflare Worker

适合不想运维的场景。需要 Cloudflare 账号。

```bash
cd worker
npm install

# 1. 建 D1 数据库，把输出的 database_id 填进 wrangler.toml
npx wrangler d1 create hookbox

# 2. 建表
npm run db:init

# 3. 生成随机 token 并写入 secret
openssl rand -hex 32
npx wrangler secret put RELAY_TOKEN
npx wrangler secret put GITHUB_SECRET      # 可选
npx wrangler secret put GENERIC_SECRET     # 可选

# 4. 上线
npm run deploy
```

部署完得到 `https://hookbox-relay.<你的子域>.workers.dev`，接口直接在根路径上：

```
https://hookbox-relay.xxx.workers.dev/hook/github
wss://hookbox-relay.xxx.workers.dev/ws?token=<TOKEN>
```

本地调试：

```bash
npm run db:init:local
npm run dev:test        # 起在 8787，token 固定 testtoken
npm run test:ws         # 冒烟：WebSocket + 实时推送
npm run test:gh         # 冒烟：GitHub 签名校验
```

## 五、方案 B：部署到自己的服务器（Docker）

### 5.1 构建

**A. 本地交叉编译 + 上传（推荐）**

```bash
cd server
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -ldflags="-s -w" -o hookbox-linux-amd64 .
```

产物约 9.5 MB，纯静态，不依赖 glibc。

**B. 在服务器上从源码构建**

把 `docker-compose.yml` 里的 `dockerfile: Dockerfile.prebuilt` 改成 `dockerfile: Dockerfile`。

> ⚠️ 注意内存。见 3.1。

### 5.2 上传与启动

```bash
# 服务器上建目录
ssh user@your-server 'mkdir -p ~/projects/hookbox'

# 上传三个文件
scp hookbox-linux-amd64 Dockerfile.prebuilt docker-compose.yml \
    user@your-server:~/projects/hookbox/

# 生成 .env（只做一次，注意 umask）
ssh user@your-server 'cd ~/projects/hookbox && umask 077 && \
  printf "RELAY_TOKEN=%s\nGITHUB_SECRET=\nGENERIC_SECRET=\n" "$(openssl rand -hex 32)" > .env'

# 构建并启动
ssh user@your-server 'cd ~/projects/hookbox && docker compose -p hookbox up -d --build'
```

`-p hookbox` 显式指定 compose 项目名。**这一条很重要**——如果机器上还跑着别的 compose 项目，不加 `-p` 可能导致项目名冲突，`docker compose down` 时误伤其他服务。

### 5.3 nginx 反向代理

新建 `/etc/nginx/sites-available/<你的域名>`：

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name your-domain.com;

    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name your-domain.com;

    ssl_certificate     /path/to/fullchain.crt;
    ssl_certificate_key /path/to/private.key;

    client_max_body_size 2m;

    location = /hookbox {
        return 301 /hookbox/;
    }

    location /hookbox/ {
        proxy_pass http://127.0.0.1:18080/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket 长连接必需
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_buffering off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }

    location / {
        return 404;
    }
}
```

**四个容易踩的点：**

1. `proxy_pass` 结尾的 `/` 不能少。它负责把 `/hookbox/` 前缀剥掉，少了就变成 404。
2. `Upgrade` 和 `Connection` 两个头必须转发，否则 WebSocket 握手失败（表现为 App 一直"连接中"）。
3. `proxy_read_timeout` 默认 60 秒，长连接会被掐断，必须调大。
4. 用 `/hookbox/` 前缀而不是根路径，是为了把域名根路径留给以后的正式站点。

启用：

```bash
sudo ln -s /etc/nginx/sites-available/your-domain /etc/nginx/sites-enabled/
sudo nginx -t          # 必须先测，通过才重载
sudo systemctl reload nginx    # reload 是优雅重载，不断现有连接
```

### 5.4 验证清单

按顺序跑，每一步都要过。

```bash
BASE=https://your-domain.com/hookbox
T=<RELAY_TOKEN>

# 1. 健康检查
curl -s $BASE/healthz
# 期望：ok

# 2. 投递
curl -s -X POST "$BASE/hook/test?token=$T" \
  -H 'content-type: application/json' \
  -d '{"title":"部署验证","body":"hello"}'
# 期望：{"ok":true,"id":"test:...","duplicate":false}

# 3. 幂等
# 再发一次完全相同的请求
# 期望：{"ok":true,"id":"test:...","duplicate":true}

# 4. 鉴权
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$BASE/hook/test?token=wrong" -d '{}'
# 期望：401

# 5. WebSocket
node -e '
const T = process.argv[1], B = process.argv[2];
const ws = new WebSocket(B.replace("https://","wss://") + "/ws?token=" + T);
ws.onopen = () => console.log("OPEN");
ws.onmessage = e => console.log("RECV", e.data);
setTimeout(async () => {
  await fetch(B + "/hook/wstest?token=" + T, {
    method: "POST", headers: {"content-type":"application/json"},
    body: JSON.stringify({title:"实时推送", body:"ok"})
  });
}, 800);
setTimeout(() => process.exit(0), 3000);
' "$T" "$BASE"
# 期望：OPEN → RECV hello → RECV msg
```

实测输出参考：

```
ok
{"duplicate":false,"id":"test:9f2c1a…","ok":true}
{"duplicate":true,"id":"test:9f2c1a…","ok":true}
401
OPEN ✅
RECV {"ts":1792569550421,"type":"hello"}
RECV {"data":{"source":"wstest","title":"实时推送","body":"ok",...},"type":"msg"}
```

### 5.5 GitHub 签名专项验证

配了 `GITHUB_SECRET` 之后，用真实签名测一遍：

```bash
node -e '
import("node:crypto").then(({default: crypto}) => {
  const body = JSON.stringify({
    action: "completed",
    workflow_run: { name: "build", conclusion: "failure" },
    repository: { full_name: "acme/api" }
  });
  const sig = "sha256=" + crypto.createHmac("sha256", process.env.SECRET).update(body).digest("hex");
  const url = process.env.BASE + "/hook/github";
  const send = (label, headers) => fetch(url, {
    method: "POST", headers: {"content-type":"application/json", ...headers}, body
  }).then(r => r.text().then(t => console.log(label, r.status, t)));

  send("合法签名  ", {"X-Hub-Signature-256": sig, "X-GitHub-Event": "workflow_run", "X-GitHub-Delivery": "d-1"})
    .then(() => send("错误签名  ", {"X-Hub-Signature-256": "sha256=" + "0".repeat(64)}))
    .then(() => send("没有签名头", {}));
});
' 
# 环境变量：SECRET=<GITHUB_SECRET> BASE=https://your-domain.com/hookbox
```

期望：

```
合法签名   200 {"duplicate":false,"id":"d-1","ok":true}
错误签名   401 {"error":"bad_signature","ok":false}
没有签名头 401 {"error":"missing_signature","ok":false}
```

- 新增 1 个 nginx 站点文件（原有站点配置未改动）

### 7.4 该机器的两个特殊约束

**① Docker Hub 完全不可达**

`/etc/docker/daemon.json` 里配了多个镜像加速源，实测全部失效，`docker pull alpine` 会永久挂起。

所以镜像基底用的是机器上已有的 `node:18-slim`。我们是静态 Go 二进制，运行时与 node 无关，只是借它的根文件系统、ca-certificates 和一个现成的非 root 用户 `node`（uid 1000）。

**以后要在这台机器上部署新镜像，会再遇到同样的问题。** 解决办法二选一：

```bash
# 办法一：在能上网的机器上 docker save / docker load
docker save myimage:tag | gzip > img.tgz
scp img.tgz server:/tmp/ && ssh server 'docker load < /tmp/img.tgz'

# 办法二：找可用的镜像加速源，写进 daemon.json（需要重启 docker）
```

**② 端口占用密集**

SSH、80、443、以及十余个业务端口都已被占用。选端口前务必 `ss -tln` 确认，具体清单见 `docs/内部部署记录.md`。

## 八、回滚

按需选择粒度。

```bash
# 只停服务，保留数据和 nginx 配置
docker compose -p hookbox stop

# 停服务并删除容器和网络，保留数据卷
docker compose -p hookbox down

# 彻底清除（含数据）
docker compose -p hookbox down
docker volume rm hookbox_hookbox-data

# 撤销 nginx 配置
sudo rm /etc/nginx/sites-enabled/your-domain.com /etc/nginx/sites-available/your-domain.com
sudo nginx -t && sudo systemctl reload nginx

# 极端情况下恢复整个 nginx 配置
sudo cp -a <nginx配置备份目录>/* /etc/nginx/
sudo nginx -t && sudo systemctl reload nginx
```

删除代码目录：`rm -rf /opt/hookbox`

## 十、附录：完整配置文件

### docker-compose.yml

```yaml
name: hookbox

services:
  relay:
    build:
      context: .
      dockerfile: Dockerfile.prebuilt
    image: hookbox-relay:0.1.0
    container_name: hookbox-relay
    restart: unless-stopped
    env_file: .env
    environment:
      ADDR: ":8080"
      DB_PATH: "/home/node/data/hookbox.db"
    volumes:
      - hookbox-data:/home/node/data
    ports:
      - "127.0.0.1:18080:8080"
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
    security_opt:
      - no-new-privileges:true

volumes:
  hookbox-data:
```

### Dockerfile.prebuilt

```dockerfile
FROM node:18-slim

WORKDIR /home/node/app
COPY --chown=node:node hookbox-linux-amd64 /home/node/app/hookbox
RUN chmod +x /home/node/app/hookbox \
 && mkdir -p /home/node/data \
 && chown -R node:node /home/node/app /home/node/data

ENV DB_PATH=/home/node/data/hookbox.db
EXPOSE 8080
USER node

ENTRYPOINT ["/home/node/app/hookbox"]
```

### .env

```
RELAY_TOKEN=<openssl rand -hex 32 生成>
GITHUB_SECRET=
GENERIC_SECRET=
```

### 环境变量一览

| 变量 | 默认 | 说明 |
|---|---|---|
| `ADDR` | `:8080` | 监听地址 |
| `DB_PATH` | `/data/hookbox.db` | SQLite 文件路径 |
| `RELAY_TOKEN` | 无 | **必填**，少于 16 位拒绝启动 |
| `GITHUB_SECRET` | 空 | GitHub webhook secret |
| `GENERIC_SECRET` | 空 | 通用 HMAC 密钥，也用于 GitLab |

### 数据库结构

```sql
CREATE TABLE messages (
  id     TEXT PRIMARY KEY,   -- 去重键
  source TEXT NOT NULL,      -- 来源标签
  title  TEXT NOT NULL,
  body   TEXT NOT NULL DEFAULT '',
  level  TEXT NOT NULL DEFAULT 'info',
  ts     INTEGER NOT NULL,   -- 毫秒时间戳

);
```
